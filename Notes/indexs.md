# Отчет по оптимизации запросов выборки задач

## 1. Сравнительный анализ планов выполнения

### До оптимизации (Одиночный индекс на `owner_id`)

База данных использовала дефолтный индекс `tasks_task_owner_id_db3dcc3e`. Из-за этого СУБД могла быстро найти только
пользователя, но внутри выборки ей приходилось вручную перебирать строки в памяти:

* **Фильтрация в RAM:** `Filter: completed`
* **Лишнее чтение:** Из памяти было удалено **264** невыполненных таски (`Rows Removed by Filter`).

### После оптимизации (Композитный индекс `(owner, completed)`)

После добавления композитного индекса `task_owner_completed_idx` планировщик стал использовать его:

* **Точечный поиск:** Оба условия проверяются на этапе сканирования индекса (`Index Cond`).
* **Эффективность:** Из памяти удалено **0** строк. База сразу вернула ровно 236 целевых записей.

---

## 2. Почему композитный индекс эффективнее в данном сценарии?

При поиске по двум полям одиночный индекс по `owner_id` заставляет базу выполнять дополнительную работу по фильтрации
данных, а индекс по булевому полю `completed` неэффективен из-за низкой селективности (данные делятся всего на два
типа).

Композитный индекс строит единую двухуровневую структуру. Он группирует данные сначала по пользователю, а внутри этой
группы они уже отсортированы по статусу выполнения. Это позволяет базе за один проход забирать чистый результат без
накладных расходов.
